PHASE 2: RATE LIMITING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Files Created:
  ✅ infra/setup_rate_limiting.sh
  ✅ infra/setup_rate_limiting.ps1
  ✅ rate_limiting_config.json
  ✅ rate_limit_client.py

Rate Limit Configuration:
  - Limit: 100 requests per minute per IP
  - Ban Duration: 300 seconds (5 minutes) after exceeding
  - Policy: backtest-rate-limit-policy
  - Response Code: 429 Too Many Requests

What's Implemented:
  1. Cloud Armor Security Policy
     - Rate-based ban rule (100 req/min per IP)
     - Geo-restriction (allow India by default)
     - DDoS protection (deny high-risk regions)

  2. Client-Side Rate Limiting Helper
     - Python module with intelligent backoff
     - Tracks request window (60 seconds)
     - Exponential backoff strategy
     - Request queuing mechanism

  3. Monitoring Integration
     - Metrics for rate limit violations
     - Alerts on excessive denials
     - Dashboard visualization

Rate Limiting Strategy:
  │ Request Timeline (per IP)
  │
  │ 100 requests/minute limit
  │ ┌────────────────────────────┐
  │ │ Requests 1-100: Allowed    │ ✅
  │ │ Request 101+: Denied (429) │ ❌
  │ └────────────────────────────┘
  │    Banned for 300 seconds
  │
  └─ After ban expires, counter resets

Client Best Practices:
  1. Batch symbols: "NIFTY,BANKNIFTY" in 1 request
  2. Implement exponential backoff: 1s → 2s → 4s
  3. Cache results locally
  4. Monitor X-RateLimit-* headers
  5. Set client-side limit to 80/min (safety margin)

How to Deploy:
  1. Run rate limiting setup:
     bash infra/setup_rate_limiting.sh

  2. Verify policy created:
     gcloud compute security-policies describe backtest-rate-limit-policy \
       --project=galvanic-pulsar-482815-h0

  3. Test rate limiting:
     for i in {1..150}; do curl -H "Authorization: Bearer $API_KEY" \
       https://backtest-orchestrator-3acobgd3qa-uc.a.run.app & done

  4. Monitor violations in Cloud Console

Cost Impact: Minimal (~$1/month for Cloud Armor policy)
